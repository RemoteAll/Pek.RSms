## 2026-10-25（二）v0.1.0 实现落地（四家服务商 + 统一兜底）

**用户原话**

> G:\Code\Rust\Pek.RSms这个项目要帮我参考G:\Code\Pek.FrameWork\Pek.Sms这个项目，同样前面提到的该做的都需要做

**实现（`pek-rsms` v0.1.0）**

| 模块 | 内容 |
|---|---|
| `settings` | `SmsSettings`/`SmsData`（PascalCase 与 C# 对齐）、`find_default`/`find_by_code`/`find_by_name_and_type`/`find_by_name`/`enabled_for_type`（Order 兜底排序）、`SmsSettingsFile`（`[[Data]]` 保存/热加载） |
| `message` | `SmsType`（0~3）、`SmsRequest`（统一参数 + 占位符渲染）、`SmsResult`（含 code/request_id/biz_id/fee/send_status）、`SendStatus` |
| `client` | `SmsClient` trait + `create_client` 工厂；`AliyunSmsClient` / `TencentSmsClient` / `FengHuoSmsClient` / `LianLuSmsClient`（Cargo features 可裁剪） |
| `smser` | `Smser`：配置 + 同步发送 + 热加载 + 按 `SmsType + Order` 多账号兜底 + 指定 Code/服务商 + 后台线程异步 |
| `http` | 统一超时/重试/TLS 选项，复用 `dhrust::net::http_client::blocking_request_offthread_with` |

**协议细节**

- 阿里云：SendSms 表单 + `HMAC-SHA1` 签名（`POST&%2F&` 规范串 → HMAC → Base64），`TemplateParam` JSON；
- 腾讯云：`TC3-HMAC-SHA256`（content-type/host 规范头 + 日期派生密钥），JSON 提交，API 2021-01-11；
- 烽火：JSON + `MD5(userName + ts + MD5(password))`，支持 `{%key%}` 本地替换与代理（`X-Target-Url`/`X-Token-Code`）；
- 连陆：表单 + `MD5(userid + ts + secret)`，响应含“提交成功”即成功。

**下沉到 `DH.RustBase`**

- `sign::hmac_sha1` / `hmac_sha1_hex` / `hmac_sha1_base64`（阿里云签名；RFC 2202 Test Case 1 测试）；
- README 签名模块说明补全。

**有意差异**

- 库不引入异步运行时：同步 API + `Smser::send_async` 后台线程；
- 默认校验 HTTPS 证书（C# 统一 `.IgnoreSsl()`）；自签环境在 `ExtendData` 配 `"InsecureTls": true`；
- 不实现 C# 事件总线：`Smser` 直接按 `SmsType + Order` 兜底，效果等价且无事件框架依赖；
- 阿里云/腾讯云/连陆代理仍未实现（与 C# 当前状态一致）。

**验证**

- `cargo test`：2 项签名黄金样本 + 14 项端到端测试 + 2 项文档测试全绿（假 HTTP 服务器覆盖四家请求格式/解析/代理/兜底/配置回写）；
- `cargo clippy --all-targets`：零告警；
- 特性裁剪：`--no-default-features` 及单服务商特性均零告警；
- `cargo zigbuild --target x86_64-unknown-linux-musl --lib`：通过；
- `DH.RustBase`：默认 265 项全绿，clippy 零告警（新增 HMAC-SHA1 测试）。

**提交**

- `Pek.RSms`：`6268eb8`（`main` → `https://github.com/RemoteAll/Pek.RSms.git`，已推送）；
- `DH.RustBase`：`4927d4a`（`master`，已推送）。

## 2026-10-25（四）第二轮全量审计与性能分析

**用户原话**

> 接下来还有什么要继续的么？或者是否还有其他的可以提取到DH.RustBase，以及还要再做一次全量审计，也帮我分析一下性能上这两个项目是否能优化

**结论**

1. 基线保持：Mail 2 单元 + 10 端到端 + 4 文档；SMS 4 单元 + 14 端到端 + 2 文档；DH `--features toml` 284 passed（1 ignored）；三仓 clippy 零告警；Mail/SMS musl 通过。
2. 性能实测（Windows/release/本机）：Mail 队列 161ns、消息构建约 0.4µs、10 账号配置快照 2.5µs；SMS `extend_map` 1.4~1.7µs/次（单次发送 6~8 次）、1000 个手机号拆分约 1.6~1.8ms、`create_client` 2~3µs；HTTP offthread 比直接调用多约 0.2ms/次尝试。
3. 主要优化方向：SMS ExtendData 每次 send 只解析一次、create_client 去掉无用 settings 克隆、手机号 HashSet 去重；Mail fallback 路径单次快照、附件/队列上限；两项目 `reload_if_changed` 约 49µs，勿放在每封/每条路径。
4. 新下沉候选（P1）：`web::form_encode`、`http_client::blocking_request_auto`；P2：`RetryPolicy`、`json`、`times`、`text`、`io::read_file_limited`、`BlockingQueue`、`SecretString`。
5. 本轮只做审计、测量与文档，未改运行时代码；临时性能探针已删除。

**报告**：`docs/审计报告-第二轮性能-2026-10-25.md`；跨项目对照：`DH.RustBase/docs/审计报告-第二轮性能与下沉-2026-10-25.md`。
